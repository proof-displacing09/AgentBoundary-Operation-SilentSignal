# SECURITY — Lab boundaries & responsible use

- AgentBoundary is a **local, synthetic-data security lab**. All organizations, people, hosts, IPs, alerts, and cases are fictional fixtures.
- Never connect it to a real SIEM, EDR, SOAR, cloud control plane, email account, ticket system, or any production data.
- `simulate_isolation` and `change_case_status` mutate only the isolated lab database. `draft_response` creates a local unsent artifact. There is no shell, network-target, credential, or mail capability in the tool registry — by design, not by prompt.
- Attacker-controlled fixture text is inert data. It is never executed as code, SQL, shell, template, or a policy expression.
- **Weak mode** (deliberately vulnerable baseline) exists only as an offline CLI (`AGENTBOUNDARY_UNSAFE_LAB=1`, separate throwaway DB, named omissions). There is no API or UI switch. Never expose a weak-mode backend on a network.
- The persona selector is a **local lab session mechanism, not production authentication/SSO**.
- Public demos, if any, must be read-only sanitized snapshots.
- Found a real bug in the lab itself? Report it privately to the project owner; do not test this software against systems you do not own or have explicit authorization to test.

## Local persistence boundaries (E8-01, T10-01/02/04, A11-01–A11-04, RC12-01–RC12-02)
- Exactly one app worker per database file, enforced by a POSIX `flock` on `<db>.applock` held for the process lifetime. The lock file is derived from the **canonical** database path (symlinks resolved), so a symlink alias and its target contend for the same lock; the lock is acquired **before** any Store is constructed, so a denied second instance cannot seed, repair, or migrate anything. If the path identity changes during acquisition, startup fails closed. An existing database file with more than one hard link is refused outright (RC12-01): hard links share one inode under different pathnames, so pathname locks alone could never give them one owner — the lab claims one worker per database file with hardlinked files rejected, not inode-level exclusivity for accepted pathnames. On non-POSIX hosts the lock file is still created but OS exclusivity is **not** enforced (documented limitation, not portability).
- Lab sessions are server-held tokens stored in the database — which is why reset backups are sensitive files, not just data copies: the pre-reset snapshot is a verified sqlite3 online backup whose **temp file is created 0600 before SQLite ever opens it** (never 0644 under any umask), whose mode is re-validated after verification and after the atomic rename (a final file that cannot be made private is removed, not left world-readable), whose destination journal is kept in memory so no transient sidecar carries backup pages, and which is Git-ignored by narrow patterns, retained newest-5, and reported by basename only. Any backup failure — including raw sqlite3 errors — refuses the reset with structured `RESET_BACKUP_FAILED`, removes the temp file and its sidecars, and leaves the original database untouched.
- A Store whose construction fails (seed, migration, repair, fixture validation, disk error) releases its opened connection and its live-connection registration exactly once before re-raising; no failed constructor can leak a counted connection.
- The global reset is one transaction (RC12-02): schema rebuild, fixture inserts, and the preserved admin session commit together or roll back together. Any reset-stage failure returns structured `RESET_FAILED` (distinct from backup-stage `RESET_BACKUP_FAILED`), leaves the previous lab state intact, retains the pre-reset backup, clears the reset barrier, and does not clear idempotency — only a successful reset does.
